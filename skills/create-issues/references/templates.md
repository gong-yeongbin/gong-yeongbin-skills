# 템플릿 단일 출처 — intent.md · spec.md · 이슈 base

create-issues 가 만드는 모든 문서의 골격이다. 다른 reference 는 이 파일을 가리키기만 하고 골격을 복제하지 않는다.

`<DOC_DIR>` 은 문서 폴더다. 작성 시점에는 `intent/_tmp/<slug>/` 이고, Stage 3 에서 GitHub 대상은 `intent/<구간>/<iid>-<slug>/`, Notion·file 대상은 `intent/<slug>/` 로 옮긴다 (`stage-3-issues.md` 3-4).

---

## 1. intent.md

```markdown
# Intent: <한 줄 목적 — 무엇을 왜 바꾸는가>

Author: <git user.name> (<git user.email>). Status: draft. Date: <YYYY-MM-DD>.

## Problem

<지금 할 수 없는 것, 누가 언제 아픈가, 왜 지금인가. 제안자의 말로 2~4 문단.>

## Proposed outcome

- <끝났을 때 관찰되는 상태. 구현 방법은 쓰지 않는다.>

## Affected users and systems

- 사용자: <영향을 받는 사람·역할>
- 시스템: <저장소·모듈·외부 시스템·데이터>

## Constraints

- <지켜야 할 정책·계약·기술 제약·금지 사항>

## Out of scope

- <이번에 하지 않는 것. 헷갈릴 수 있는 인접 작업을 명시>

## Open questions

- <인터뷰에서 미결로 남긴 것만. 답이 나온 것은 위 섹션으로 옮긴다. 없으면 `- 없음.`>
```

작성 규칙.
- Status 는 Stage 1 게이트에서 `y` 를 받으면 `accepted` 로 바꾼다.
- **구현 결정은 intent 에 쓰지 않는다.** 판별 기준은 문장에 도구명·스킬명·파일 경로·명령·함수명이 있는가다. 있으면 구현 결정이고 spec 몫이다. "무엇을 지켜야 하는가"(정책·계약·금지)만 Constraints 에 남긴다. 예. `커밋은 승인 뒤에만` 은 Constraints, `배포는 X 스크립트로 한다` 는 spec.
- 작성 직후 Constraints·Proposed outcome 을 위 기준으로 훑어 걸리는 줄을 "spec 으로 이월" 메모로 빼둔다. Stage 1 게이트 표에 건수를 보인다.
- 시점에 따라 변하는 수치(항목 수·총계·버전)는 절대값으로 쓰지 않는다. 필요하면 "작성 시점" 을 붙이고 성공 기준에는 넣지 않는다.
- 길이. Problem 2~4 문단, 나머지 섹션은 각 3~8줄. intent 가 spec 만큼 길어지면 경계가 흐려진 신호다.

## 2. spec.md

```markdown
# Spec: <작업 제목> (from intent.md <YYYY-MM-DD>)

Status: draft. Intent: ./intent.md

## Problem Statement

<사용자 관점의 문제. intent 의 Problem 을 요구사항 언어로 다듬는다.>

## Solution

<사용자 관점의 해법. 무엇이 어떻게 달라지는가.>

## User Stories

1. As a <actor>, I want <feature>, so that <benefit>

<정상·예외·경계·운영 관점을 모두 덮는다.>

## Facts (조사 결과)

| # | 사실 | 출처 (파일·조회·명령) | 확인일 |
| --- | --- | --- | --- |
| F1 | <결정에 영향을 주는 실측> | <파일:줄 · SQL · 명령> | <날짜> |

<아래 결정이 근거로 삼는 것만 적는다. 추정은 넣지 않는다. 확인하지 못한 것은 "미확인" 으로 적고 그 위에 결정을 세우지 않는다.>

## Implementation Decisions

- D1. <만들거나 바꿀 모듈과 인터페이스> — 근거: F<n> | 사용자 결정(Q<n>) | intent Constraints | baseline(<섹션명>)
- D2. <아키텍처·스키마·API 계약·입력과 결과 계약> — 근거: …
- D3. <범위·기간·경계·기본값. 예. 백필 범위는 최초 기록일(F1) 전날부터 어제까지> — 근거: F1
- D4. <검토했다가 기각한 대안과 이유>

## Testing Decisions

- 좋은 테스트의 기준. <외부 행동만 검증, 구현 세부 검증 금지>
- 테스트할 seam. <가능한 가장 높은 seam. 기존 seam 우선. 새 seam 은 최소>
- 테스트 대상 모듈. <...>
- 선행 사례. <코드베이스의 유사 테스트>
- 검증 게이트. <프로젝트 품질 게이트 명령과 기준>

## Out of Scope

- <이번 spec 이 다루지 않는 것>

## Further Notes

- <남은 메모. 미결 질문은 "미결" 표기>

---
Generated by create-issues · grill <YYYY-MM-DD> · 요구사항 원문 요약: <한 줄>
```

작성 규칙.
- Status 는 Stage 2 게이트에서 `y` 를 받으면 `accepted` 로 바꾼다.
- 프로젝트 도메인 용어(CLAUDE.md·용어집·ADR 의 이름)를 그대로 쓴다.
- intent 의 Open questions 는 spec 에서 답하거나 Further Notes 에 "다음 작업으로 이월" 로 남긴다. 조용히 사라지게 하지 않는다.
- User Stories 는 작업 규모에 비례한다. 기능·API 작업은 정상·예외·경계·운영을 촘촘히(10건 안팎), 배포·문서·설정 작업은 3~6건. 검증 메모는 스토리가 아니라 Testing Decisions 에 쓴다.
- **파일 경로.** 코드 작업에서는 구체 파일 경로·코드 조각을 쓰지 않는다 (금방 낡는다). 산출물이 파일 그 자체인 작업(배포·문서·설정)은 예외로 대상 경로를 적는다. 검증 명령은 어느 작업이든 1개까지.
- 시점 의존 수치는 상대 조건으로 쓴다. `총계가 45` 가 아니라 `총계가 배포 전 N 에서 N+1 로`.
- 검증 증거는 검증 대상과 독립이어야 한다. 이 문서를 만든 실행 자체를 "동작 증거" 로 삼지 않는다.
- **모든 D 에 번호와 `— 근거:` 를 붙인다.** 근거는 F·Q·intent·baseline 중 하나다. 어디에도 없으면 그 결정을 쓰지 않는다. 관례 값("운영 시작일부터", "기본 30일")은 근거가 아니다. 관례를 쓰려면 실측 F 가 관례와 같음을 확인해 적고, 다르면 실측을 따른다.
- 범위·기간·경계·기본값은 항상 명시적 결정이다. 행동("백필한다")만 있고 값이 없는 결정은 미완이다.

## 3. 이슈 base 본문 (대상 중립)

base 는 GitHub·Notion·파일 공통 부분이다. wrapper(phase 마커, `## Blocked by`, 대상별 메타데이터 줄)는 게시 직전에 조립한다 (§4). base 에는 wrapper 를 넣지 않는다. 참조 정보는 `### 메타데이터` 한 곳에 모으고 별도 `## 참조` 섹션을 만들지 않는다.

### 3-1. 구현 이슈 base (`<TMP>/<slug>_solve.md`)

```markdown
## What to build

<1~2 문장. 이 이슈가 끝났을 때의 종단 행동을 사용자 관점으로.>

### 메타데이터

- 작업명: <title>
- 작업 종류: <기능 추가 / 버그 수정 / 리팩터링 / 문서 / 운영 ...>
- 관련 모듈: <spec Implementation Decisions 의 모듈명>
- intent: `<DOC_DIR>/intent.md`
- spec: `<DOC_DIR>/spec.md`

### 핵심 결정 사항

- <spec Implementation Decisions 중 구현자가 spec 을 열지 않고 시작해도 틀리지 않을 것만. 최대 5줄, 항목당 1줄. 나머지는 "상세는 spec §Implementation Decisions" 한 줄로.>

### 선행 작업

- [ ] <외부 의존. 없으면 섹션 생략>

### 작업 라인업

- <만들거나 바꿀 대상. 코드 작업이면 모듈·계층, 문서 작업이면 문서 목록>

## Acceptance criteria

### 진행 단계 체크리스트

- [ ] (1) <단계> (D<n>)
- [ ] (2) <단계> (D<n>, D<m>)

### 완료 조건 (DoD)

- [ ] <spec Testing Decisions 의 검증 게이트 통과>
- [ ] <구현 몫 User Stories 충족 확인 (US 번호 나열). TEST 이슈가 없으면 "User Stories 전부 충족 확인">
```

체크리스트 항목 규칙. 항목마다 끝에 근거 결정 번호 `(D<n>)` 을 붙인다. 붙일 D 가 없는 항목은 만들지 않는다. 값(날짜·범위·건수·기본값)이 든 항목은 그 값이 D 에 그대로 있어야 한다. spec 에 없는 값이 체크리스트에서 처음 등장하면 규칙 위반이며, Stage 2 로 돌아가 F 확인 → D 추가 뒤 다시 온다.

구현 이슈 체크리스트·DoD 에 넣지 않는 것.
- **TEST 로의 인계 항목.** 구현 담당이 할 일이 아니라 늘 "자기 몫 아님" 사유만 남는다.
- **TEST 몫 User Story 검증.** 스토리마다 검증을 맡을 이슈를 하나만 정한다. 구현 담당이 자기 환경(단위·슬라이스 테스트)에서 끝낼 수 있는 스토리는 구현 DoD 에, 실DB·대조·운영 환경이 필요한 스토리는 TEST 이슈에만 둔다. 같은 스토리를 두 이슈에 두지 않는다.
- **커밋·Status 전환.** 담당 밖인 항목이다.

### 3-2. TEST 이슈 base (`<TMP>/<slug>_test.md`) — TEST 있을 때만

```markdown
## What to build

구현 이슈의 변경을 독립적으로 검증한다. <무엇을 어떤 수준으로 검증하는지 1~2 문장.>

### TEST 대상 메타데이터

- 대상: <모듈 / 엔드포인트 / 시나리오>
- 테스트 종류: <단위 / 통합 / E2E / 수동 검증>
- intent: `<DOC_DIR>/intent.md`
- spec: `<DOC_DIR>/spec.md` §Testing Decisions

### 테스트 케이스

| # | 케이스 | 입력 | 기대 결과 |
| --- | --- | --- | --- |
| 1 | <정상> | ... | <관찰 가능한 결과. 시점 의존 수치는 상대 조건으로> |
| 2 | <예외> | ... | ... |
| 3 | <경계> | ... | ... |

### 테스트 데이터 / 환경

- <시드·환경·실행 명령>

## Acceptance criteria

### 검증 게이트

- [ ] (1) <케이스 작성> (D<n>)
- [ ] (2) <실행·통과> (D<n>)
- [ ] (3) <회귀 없음> (D<n>)

### 산출물

- [ ] <baseline `## TEST 이슈 산출물 템플릿` 이 있으면 그 목록, 없으면 grill 결정>

### 완료 조건 (DoD)

- [ ] 모든 검증 게이트 통과
- [ ] 결과를 TEST 이슈에 기록
```

### 공통 규칙

- 첫 H2 는 `## What to build`, 두 번째 H2 는 `## Acceptance criteria`. 사이에 다른 H2 를 넣지 않는다.
- 체크박스는 `- [ ] (N) text`. `- [ ] N. text` 는 Notion 이 nested numbered list 로 깨뜨리므로 금지.
- 파일 경로는 메타데이터의 intent/spec 경로 외에는 쓰지 않는다. 예외는 spec 과 같다 (파일이 산출물인 작업의 대상 경로와 검증 명령 1개).
- 체크리스트·DoD 에는 그 이슈의 담당이 스스로 끝낼 수 있는 항목만 넣는다.
- 제목·본문 언어는 요구사항 언어를 따른다.
- **제목은 짧게.** `<title>` 은 `<영역> - <명사구>` 로 쓴다. 명사구는 세부 조각이 아니라 작업 전체를 한 단계 위에서 본 목적·개념이다 ("이 작업은 결국 무엇을 위한 것인가"). 공백 포함 20자 이내 (영역 접두어·` - TEST` 는 세지 않는다). 조건·원인·개수·구현 방법은 `## What to build` 에 쓴다. baseline 이 제목 형식을 고정하면 그것이 우선한다.
  - `대시보드 - 완료 뒤 취소되거나 원본에서 사라진 이슈를 완료 지표에서 제외` → `대시보드 - 완료 지표 정합성 보정`
  - `조회가 느린 11개 화면 필터행 그리드에 자동완성 적용` → `필터행 자동완성 성능 개선`
- **코드 요소는 인라인 코드(백틱)로 쓴다.** 파일·디렉터리 경로, 클래스·메서드·변수명, 테이블·컬럼명, 엔드포인트, 명령·옵션, 설정 키·환경변수, 브랜치명·커밋 SHA, 스킬명. 확장자가 붙은 이름(`deploy.sh`)은 맨 글자로 두면 Notion 이 링크로 바꾸므로 예외 없이 감싼다. 외부 URL 은 텍스트 그대로 두고 감싸지 않는다. `{` 가 든 값은 Notion 이 속성 문법으로 오인하므로 코드 블록으로 빼거나 풀어 쓴다.
- base 에 `## 핵심 원칙 (고정)`, `## Blocked by`, `# 구현`, `# TEST`, 대상별 메타데이터 줄을 넣지 않는다. wrapper 는 게시 단계 몫이다.

## 4. wrapper 조립 규칙 (게시 직전)

| 부위 | GitHub 통합 본문 | Notion 구현 본문 | Notion TEST 본문 | 파일 issue-solve.md / issue-test.md |
| --- | --- | --- | --- | --- |
| 메타데이터 추가 줄 (`- spec:` 뒤) | 없음 | `- 참고 자료: <mention-page url="..."/>` (사용자 제공 Notion URL 있을 때만) | 구현과 같음 | 없음 |
| `## 핵심 원칙 (고정)` | baseline 에 정의된 경우만, H1 `# 핵심 원칙 (고정)` | baseline 에 정의된 경우만 H2 | 같음 | 구현 파일에만 H2 |
| phase 마커 | TEST 있으면 `# 구현` / `# TEST` H1. 없으면 생략 | 없음 | 없음 | 없음 |
| base | solve.md (+ test.md) | solve.md | test.md | solve.md / test.md |
| `## Blocked by` | phase 마다 1회 | `None - can start immediately` | `선행 구현 이슈는 본 페이지 선행 작업 relation 으로 연결됨.` (relation 속성이 없으면 `선행: 구현 이슈 <url>`) | solve: `None - can start immediately`, test: `선행: issue-solve.md 완료 후 진행` |

메타데이터 표기.
- 저장소 문서(intent·spec)는 **경로 텍스트만** 적는다. 커밋 SHA·"미커밋"·저장소 웹 링크를 붙이지 않는다. 파일이 저장소에 있으면 경로가 곧 참조다.
- Notion 페이지는 전부 `<mention-page url="..."/>` 로 건다. raw URL 텍스트나 markdown 링크로 적지 않는다.
- 구현↔TEST 상호 참조는 Notion 에서는 relation 속성이 담당하므로 본문에 넣지 않는다. GitHub 은 한 이슈 안의 두 phase 이므로 참조가 필요 없다.
