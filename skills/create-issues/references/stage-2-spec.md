# Stage 2 — 코드베이스 탐색 + spec 인터뷰 + spec.md

목표. 확정된 intent.md 를 요구사항·설계 명세 `spec.md` 로 바꾼다. 엔지니어가 이것만 읽고 구현 계획을 세울 수 있어야 한다. 아직 설계 결정이 열려 있는 시점이므로 탐색 결과를 전제로 인터뷰해서 결정을 받는다.

**설계 용어.** module·interface·seam·adapter·deep module 은 다음 뜻으로 쓴다. module 은 인터페이스 뒤에 구현을 감춘 단위, interface 는 호출부가 알아야 하는 전부(시그니처·불변 조건·호출 순서·에러 상황·설정), seam 은 테스트가 실제 구현 대신 대역을 끼울 수 있는 지점, adapter 는 seam 에 끼우는 구현(운영용·테스트용), deep module 은 단순한 인터페이스 뒤에 많은 기능을 감춘 모듈이다. 공용 스킬 `codebase-design` 이 설치되어 있으면(사용자 `~/.claude/skills/` 또는 프로젝트 `./.claude/skills/`) 2-1 전에 그 SKILL.md 를 파일로 읽어 용어를 맞춘다. 없으면 위 정의만으로 진행한다. 도메인은 프로젝트 용어, 구조는 이 용어로 쓴다.

## 2-1. 코드베이스 탐색 (사용자 입력 없이, 같은 턴)

intent 의 Affected systems 를 단서로 현재 상태를 파악한다. 아래 영역은 서로 독립이므로 **서브에이전트를 한 메시지에서 동시에 띄워** 결론만 받는다 (`subagent-runtime.md`). 작은 저장소라 영역 하나가 몇 초면 끝나면 직접 읽어도 된다.

### 역할 분담 — 서브에이전트는 리서치, 판단은 메인 세션

서브에이전트는 **사실과 근거를 모아 오는 일** 만 한다. 그 근거로 무엇을 결정할지(파급 범위, seam 위치, 대안 선택)는 메인 세션이 판단해 질문으로 사용자에게 올린다. 서브에이전트에게 "어느 쪽이 좋은지" 를 묻지 않는다. "후보와 근거를 전부 가져와 달라" 고 요청한다.

### 모델은 리서치 깊이로 고른다

`haiku` 는 쓰지 않는다. 최소는 `sonnet`, 기본은 `opus` 다.

| 리서치 깊이 | 예 | 서브에이전트 | `model` |
| --- | --- | --- | --- |
| **얕음.** 답이 파일에 그대로 있고 읽어서 옮기면 끝난다 | 빌드·테스트 명령, 파일·클래스 위치, 용어 정의, `intent/` 선행 폴더 나열 | `Explore` | `"sonnet"` |
| **깊음 (기본).** 여러 파일을 읽어 관계를 엮어야 한다. 놓치면 spec 이 틀린다 | 호출처 전수와 파급 경로, 기존 테스트 방식과 seam 후보, 숨은 계약(예외·정렬·NULL 동작), 레거시 로직 동작, ADR·도메인 결정 | `Explore` 또는 `general-purpose` | `"opus"` |

기준은 하나다. **놓친 사실이 spec 의 결정을 바꿀 수 있는가.** 바꿀 수 있으면 깊음이고 `opus` 다. 애매하면 깊음으로 둔다.

| 영역 | 요청할 것 (근거 수집) | 기본 깊이 |
| --- | --- | --- |
| 품질 게이트 | CLAUDE.md 등의 빌드·테스트·린트 명령 | 얕음 |
| 선행 사례 | 같은 패턴의 이전 이슈·`intent/` 폴더와 그 요지 | 얕음 |
| 도메인 | CONTEXT.md·용어집·ADR 에서 이 작업에 닿는 용어와 결정 | 깊음 |
| 테스트 | 기존 테스트의 위치·방식·픽스처. seam 후보 전부와 각 seam 의 adapter 개수(운영·테스트). interface 를 건너뛰어 내부를 단언하는 기존 테스트 후보 | 깊음 |
| 모듈 | 닿는 모듈과 공개 인터페이스(시그니처 외에 불변 조건·호출 순서·에러 상황·설정). 호출처 전수. 바꿀 때 깨질 수 있는 계약 후보. interface 가 implementation 만큼 복잡한 shallow 후보 | 깊음 |

"기본 깊이" 는 출발점이다. 단순 문서 변경이면 모듈·테스트 영역도 얕음으로 내려갈 수 있다.

요청 문구는 "사실·후보·근거 경로만, 결정이나 추천은 하지 말 것, 파일 본문 인용 금지, 확인하지 못한 것은 그렇게 표시" 로 고정한다.

탐색 결과는 다음 질문의 전제로 쓰고, **결정에 영향을 주는 사실은 spec `## Facts` 의 씨앗으로 보관** 한다 (F 번호·출처·확인일). 메시지로 길게 보고하지 않는다. "사실상 전량이 X 이후, 예외 N건" 처럼 예외가 붙은 사실은 예외를 따로 F 로 쪼갠다. 예외가 뒤에 결정을 뒤집는 경우가 많다.

데이터를 다루는 작업이면 반드시 실측한다. 대상 데이터의 실제 시작·끝, 건수, 비어 있는 구간, 기존 지표·설정의 하한값과 그것이 실측과 같은지. "운영 시작일" 같은 관례 상수는 실측과 대조한 뒤에만 쓴다.

## 2-2. spec 인터뷰 (한 번에 하나씩)

`grilling.md` 절차로 질문을 하나씩 묻는다. 프론티어 씨앗.

| spec 섹션 | 질문 씨앗 |
| --- | --- |
| Solution | 사용자가 보는 해법의 모양. 대안이 둘 이상이면 숫자 선택지로 제시하고 추천을 단다. |
| User Stories | 빠진 actor 가 없는가 (운영자·관리자·배치·외부 시스템). 예외·경계 스토리. |
| Facts | 탐색으로 확보한 사실 중 결정을 좌우할 것을 확인시킨다. "실측은 X 인데 관례는 Y 다. 어느 쪽을 기준으로 하나" 는 반드시 질문으로 올린다. |
| Implementation Decisions | 만들거나 바꿀 모듈과 인터페이스(불변 조건·에러 상황까지). 스키마·API 계약 변경. 기각할 대안. 깊은 모듈로 뽑을 수 있는 곳. 새 모듈은 삭제 테스트(지우면 복잡도가 호출부로 되돌아오는가)를 통과해야 하고, 넘겨주기만 하는 모듈은 만들지 않는다 (프로젝트가 정한 계층 구조는 예외). **범위·기간·경계·기본값**(시작일·끝·경계 건·백필 범위·페이지 크기)은 빠뜨리기 쉬우므로 씨앗에 항상 넣는다. |
| Testing Decisions | 테스트 seam. 기존 seam 우선, 가능한 가장 높은 seam, 새 seam 은 최소. seam 수는 적을수록 좋고 이상은 하나다. 인터페이스가 곧 테스트 표면이며 내부 상태를 단언하지 않는다. adapter 가 하나뿐인 seam 은 새로 만들지 않는다. 의존성 종류에 따라 대역을 정한다 (in-process 직접 / 로컬 대역 / 인메모리 adapter / mock). 모듈을 합쳐 깊게 만드는 작업이면 옛 shallow 테스트를 새 인터페이스 테스트로 **교체** 할지 결정에 넣는다. |
| Out of Scope | intent 의 Out of scope 에 설계 단계에서 드러난 것을 더한다. |
| Further Notes | intent 의 Open questions 중 여기서 답할 것과 이월할 것. |

- TEST 이슈 산출물 범위(어느 계층까지, 어떤 종류)를 이 인터뷰에서 정한다. baseline `## TEST 이슈 산출물 템플릿` 이 있으면 그것을 기본으로 보이고 조정만 받는다.
- 프론티어가 비면 인터뷰를 끝낸다.

## 2-3. spec.md 작성

1. `templates.md` §2 골격. Status `draft`. 제목 괄호에 intent.md 의 Date. 마지막 `Generated by` 줄을 채운다.
2. baseline 의 조건부 결정(예. `## Java 프로젝트 기본 결정`)을 먼저 D 로 넣고 근거를 `baseline(<섹션명>)` 으로 적는다. 그 다음 2-1 의 사실을 `## Facts` 표로 쓴다. Stage 1 에서 "spec 으로 이월" 한 구현 결정을 Implementation Decisions 에 `D<n>` 으로 넣는다. 모든 D 에 `— 근거:` 를 붙인다. 근거가 없는 D 는 쓰지 않는다.
3. **결정 누락 점검.** 작업이 데이터·기간·범위를 다루면 시작·끝·경계·기본값 결정이 D 에 있는지 확인한다. 없으면 인터뷰로 돌아가 질문 하나를 더 한다. 관례 값을 쓰는 D 는 그 관례가 F 와 같음을 확인했다는 문장을 근거에 넣는다.
4. `intent/_tmp/<slug>/spec.md` 를 `Write` 한다.
5. 프로젝트 용어를 쓴다. 경로·수치·증거 규칙은 `templates.md` §2 작성 규칙을 따른다.
6. intent 의 Open questions 를 전부 처리했는지 대조한다. 답한 것은 해당 섹션에, 이월한 것은 Further Notes 에 "이월" 표기.
7. 어시스턴트 메시지로 본문을 출력하지 않는다.

## 2-4. 확정 게이트 (사용자 입력)

```
intent/_tmp/<slug>/spec.md 를 작성했습니다. 파일을 열어 검토·수정해 주세요.

| 섹션 | 요약 |
| --- | --- |
| Solution | ... |
| Facts | N건 (미확인 M건) |
| User Stories | N건 |
| Implementation Decisions | N건, 전부 근거 표기 (범위·경계 결정 K건) |
| Testing Decisions | seam: ... |
| Out of Scope | N건 |
| Further Notes | 이월 N건 |
| TEST 이슈 | confirmed: yes (강제) | confirmed: yes | confirmed: no |

[STOP] spec 을 확정하고 Stage 3 (이슈 생성) 로 진행할까요? (y/n)
```

- `y` → 파일을 다시 `Read` 하고 Status 를 `accepted` 로 `Edit`. Stage 3 진입.
- `n` → 수정 지점을 묻고 반영 뒤 게이트 재출력.
- 비명시 응답 → 게이트 재출력.
- 게이트 메시지에 다음 단계 예고를 섞지 않는다.
