# grilling — 인터뷰 절차

Stage 1(intent)·Stage 2(spec) 인터뷰의 단일 출처다. 외부 인터뷰 스킬을 호출하지 않고 메인 세션이 직접 수행한다.

## 원리

사용자와 **공유된 이해(shared understanding)** 에 이를 때까지 끈질기게 인터뷰한다. 결정들을 **설계 트리** 로 본다. 하나의 결정은 그 아래 매달린 결정들로 갈라진다.

## 한 번에 하나씩

질문 하나를 묻고 답을 받은 뒤 다음 질문으로 간다. 한 화면에 질문 다섯 개가 쌓이면 답하기 전에 지친다. 주거니 받거니가 원칙이다.

- **프론티어** = 전제가 이미 정해져 지금 답을 추측하지 않고 물을 수 있는 질문들. 메인 세션이 내부적으로 관리하고 사용자에게 목록으로 보이지 않는다.
- 프론티어에서 **가장 상류의 질문 하나** 를 고른다. 상류란 그 답이 다른 질문을 가장 많이 풀거나 없애는 것이다. 답이 들어오면 트리를 다시 계산하고 다음 질문 하나를 고른다.
- 답 하나로 다른 질문이 사라지거나 답이 정해지면 묻지 않고 넘어간다. "이렇게 이해했다" 확인도 질문 하나로 친다.
- 정말로 짝인 두 질문(하나의 답이 다른 하나 없이는 의미가 없는 경우)만 한 번에 둘까지 묻는다. 셋 이상은 묶지 않는다.

## 질문 출력 형식

```
❓ **Q<n>** - **<질문 제목>**: <질문 본문. 선택지가 있으면 숫자 리스트.>

➡️ <추천 답. 선택지가 있으면 "N (추천)" 과 이유 한 줄.>

(남은 질문 약 <k>개)
```

- `Q<n>` 은 Stage 안에서 1부터 이어 붙인다.
- `(남은 질문 약 k개)` 는 현재 프론티어 크기다. 정확하지 않아도 된다. 사용자가 끝을 가늠하게 하는 용도다.
- 질문 본문은 짧게. 배경 설명이 필요하면 한두 문장으로 그친다. Stage 시작 시 보인 사실 확인 표를 질문마다 반복하지 않는다.

선택지 규칙.
- 선택지는 `1. / 2. / 3.` 숫자 라벨만 쓴다. 알파벳 라벨은 쓰지 않는다. 사용자가 한/영 전환 없이 숫자만 눌러 답하게 하기 위해서다.
- 추천 선택지는 항목 끝에 `(추천)` 을 붙인다.
- 사용자가 숫자만 답해도 그 선택지로 해석한다. 본문으로 답해도 의미가 맞으면 받아들인다.

## 팩트는 스스로 찾는다

- **팩트를 찾는 것은 네 일이고 사용자의 일이 아니다.** 파일시스템·코드·도구로 알 수 있는 것은 묻지 않는다. 직접 탐색하거나 `Explore` 서브에이전트에 맡긴다 (`subagent-runtime.md`).
- 탐색이 진행 중이면 그것은 "아직 정해지지 않은 전제" 다. 그 결과에 의존하지 않는 다른 질문을 먼저 묻는다. 탐색 때문에 인터뷰를 멈추지 않는다.
- **결정은 사용자의 것이다.** 결정 하나하나를 사용자에게 내놓고 기다린다. 대신 정하지 않는다.

## 종료

- 프론티어가 비면 끝이다. 설계 트리의 모든 가지를 방문했고 조용히 가정한 것이 남아 있지 않은 상태다.
- 종료 뒤 곧바로 행동하지 않는다. 결정 표를 보여 주고 **사용자가 공유된 이해에 도달했다고 확인** 한 뒤에만 문서 작성으로 간다. 이 확인이 각 Stage 의 확정 게이트다.

## 인터뷰 중 금지

- 사용자 답을 받기 전에 문서를 쓰거나 파일을 만들지 않는다. 팩트 탐색용 읽기 도구만 허용한다.
- "다음 단계로 넘어갑니다" 같은 사전 예고를 질문 메시지에 섞지 않는다. 질문 메시지는 질문·추천 답·남은 개수만이다.
- 질문을 셋 이상 한 메시지에 묶지 않는다.
- 사용자가 "계속", "진행", "ok" 처럼 답하면 결정으로 해석하지 않는다. 열린 질문을 다시 보여 주고 답을 요청한다.

## baseline 과의 관계

프로젝트 `baseline.md` 의 `## grill 제외 항목` 에 있는 결정은 이미 정해진 전제다. 질문으로 올리지 않는다. 사용자가 바꾸고 싶다고 먼저 말할 때만 재논의한다.
