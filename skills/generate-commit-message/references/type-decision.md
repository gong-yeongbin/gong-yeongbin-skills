# type 결정 기준

diff 패턴을 위에서 아래 순서로 대조해 첫 번째로 맞는 type 을 고른다. 동작 변경이 있는지 먼저 보고, 없으면 테스트·문서·포매팅·빌드·리팩터링 순으로 구분한다.

| 변경 패턴 | type | 기준 |
| --- | --- | --- |
| 테스트 파일(`*Test.java`, `*.spec.ts`, `*.test.tsx`, `__tests__/`)과 fixture 만 변경 | `test` | 운영 코드 동작 변경 없이 테스트 추가·수정 |
| README, 설계 문서, API 문서, Javadoc/JSDoc, 주석만 변경 | `docs` | 실행 동작 변경 없음 |
| 포매터·린터 설정, 들여쓰기·세미콜론·import 정렬만 변경 | `style` | 코드 의미 변경 없음 |
| `pom.xml`, `build.gradle`, `package.json`, lockfile, 번들러·CI 빌드 설정 변경 | `build` | 빌드 시스템·의존성·패키징 변경 |
| 측정 가능한 성능 개선 (인덱스, N+1 해소, 캐싱, 번들·렌더링 최적화) | `perf` | 기능은 같고 성능 지표가 좋아짐 |
| 장애·예외·오동작·응답 코드·검증 누락·UI 표시 오류 보정 | `fix` | 의도와 다르던 동작을 정상화 |
| 새 API, 새 파라미터, 새 화면, 새 UI 상호작용, 기존 동작 확장 | `feat` | 사용자가 쓸 수 있는 기능 추가 |
| 동작 불변 구조 개선, 책임 분리, 이름 변경, 중복 제거 | `refactor` | 외부 동작 변경 없이 내부 구조 개선 |
| 운영·메타·툴링·설정 정리, 생성 파일 정리, 그 외 유지보수 | `chore` | 위 어디에도 뚜렷이 속하지 않는 유지보수 |

## 백엔드 판단 보조

- `Controller`·`Service`·`Repository`·`DTO`·`Entity`·`Config` 가 함께 바뀌면 사용자 기능이 달라졌는지 먼저 본다.
- API 경로, 요청·응답 DTO, OpenAPI 명세가 바뀌면 `feat` 또는 `fix` 후보다.
- 빌드 파일만 바뀌면 `build` 다. 의존성 변경이 버그 수정의 일부면 `fix` 도 후보로 본다.

## 프론트엔드 판단 보조

- `components`·`pages`·`routes`·`hooks`·`stores`·API client 가 함께 바뀌면 화면이나 사용자 흐름이 달라졌는지 먼저 본다.
- 새 화면, 새 UI 액션, 폼 필드, 라우팅, API 연동 추가는 `feat` 후보다.
- 잘못된 렌더링, 상태 동기화 오류, validation 누락, 에러 처리 보정은 `fix` 후보다.
- 스타일 토큰 변경은 기능 변화가 없으면 `style`, 레이아웃 오류 보정이면 `fix` 다.

## 공통 판단 보조

- 테스트와 운영 코드가 함께 바뀌면 운영 코드의 목적으로 type 을 정하고, 테스트 추가는 본문 불릿에 넣는다.
- 프론트엔드와 백엔드가 함께 바뀌어도 하나의 사용자 가치나 버그 수정으로 묶이는지 먼저 본다.
- 한 diff 가 여러 영역에 걸치면 커밋을 나눠야 하는지 먼저 검토한다.

## 모호한 경우

후보가 둘 이상 동시에 맞으면 둘을 숫자 선택지로 제시하고 사용자 답을 받은 뒤 진행한다.

- 새 기능과 기존 버그 수정이 함께 있음 → `feat` vs `fix`
- 의존성 업데이트와 코드 수정이 함께 있음 → `build` vs `fix` 또는 `feat`
- 스타일 변경과 UI 오류 수정이 함께 있음 → `style` vs `fix`
- 기능 추가와 리팩터링이 섞임 → type 을 고르기 전에 커밋 분리를 제안한다
